# Ocean 下一阶段方向：功能、分析、统计、预测与加速

核对日期：2026-10-21。本文面向项目理解与后续规划，不要求读者掌握前后端编写方式。

本次读取了领域定义、路线图、需求、数据契约、主要前后端分析路径、实验脚本与实验产物，并对用户提供的已部署站点做了低频只读检查。没有部署、重建线上索引、下载全量原始资料、训练模型或进行压力测试。以下明确区分：线上返回、本地实现、已有实验和后续建议。

## 1. 推荐的项目主线

下一阶段最值得完成的任务是：

> 用户给定地点、日期和范围，系统识别附近的捕捞活动热点与锋面，量化两者的位置和时间关系，通过历史样本与非锋面对照检验稳定性，输出带依据、样本数和不确定性的关注区域。

这条主线有三个递进层级：

1. **描述事实**：最近锋面在哪里，附近哪些区域有活动，活动距离锋面多远。
2. **检验规律**：靠近锋面是否经常伴随更高活动密度，响应通常滞后几天，结论对半径与季节是否稳定。
3. **验证预测**：仅使用当时已知信息，能否比“延续昨天”和“沿用季节平均”更好地预测未来活动或锋面持续性。

可视化加速是支持用户反复筛选、比较与复核的工程支线；它与科学关系验证分别验收。项目当前已经有地图、按需出数、响应表、统计脚本与规则解释，下一步应着重把它们接成可验证分析流程。

依据：[领域定义](../../CONTEXT.md)、[产品路线图](../ocean-fishery-operation-roadmap.md)、[ADR](../adr/0001-use-apparent-fishing-effort-for-front-response.md)。

## 4. 应该分析什么、怎么分析

### 4.1 周围海域附近的捕捞活动热点

输入：用户位置与作业圈、每日完整AIS活动格点、日期、有效覆盖信息；后续可按渔具类别分层。

建议计算：

- 圈内总活动小时、有效天数、单位面积日均活动密度。
- 最近3/7/30天出现活动的有效日期比例。
- 活动在空间上是否连续集中，热点是否稳定，而不是只有单日极端值。
- 到出发点的直线距离与方位。没有路径/船速条件时不直接改写为航时、油耗或可达性。

可先使用固定网格与相邻高值区合并，定义透明阈值，再考虑更复杂聚类。阈值须由训练/探索阶段确定，不能看完测试期后挑最有利阈值。总小时与密度分别回答“总活动多不多”和“单位面积是否集中”。

页面建议：地图高亮热点，右侧显示候选区域列表、近7天曲线、有效观测天数与数据粒度。图上绘制筛选不能作为统计输入：当前AIS显示按第60分位筛选且最多700格，会省略部分活动。[绘制逻辑](../../frontend/prototype/prototype-fishing.js#L720)。

### 4.2 最近锋面与最有依据的锋面

输入：同日完整编号对象与未编号线段、出发点、SST及其有效掩码、最近多日资料。

建议计算：

- 出发点到折线的最短距离，而不是仅到锋面中心点的距离。
- 距离、方位、长度、近期出现天数、移动速度与匹配置信度。
- 两侧温差/梯度代理及有效采样数。

当前已有两侧各约10 km取样的跨锋面SST温差与梯度代理，不能再笼统说“没有任何强度信息”。但它使用独立海温来源和分档值，不是上游`frontal_intensity`，还需要分辨率与独立性验证。[代理实现](../../frontend/prototype/prototype-data.js#L636)。

结果可以分别给“最近锋面”和“证据较充分的候选锋面”。后者需要历史活动响应与覆盖支持，不能仅由长度或距离决定。新阶段先把各证据分项呈现，不急于固定50/50等新综合权重。

### 4.3 锋面与捕捞活动的位置关系

输入：同日锋面几何、全部活动格点、有效面积、冷暖侧类别，以及统一的时间和海域范围。

建议输出三类图：

1. **地图关系**：热点或格点到最近锋面的连线，颜色表示距离。
2. **距离带统计**：0-10、10-20、20-30 km等不重叠带的活动密度。每条带以有效水域面积归一化，减少“远处面积更大所以总小时更多”的影响。
3. **侧别对照**：相近距离、相同季节条件下，冷侧与暖侧的活动密度及样本数。缺少侧别时保留未知，不能单凭温差代理自动认定生态意义。

0.1°格点在本海区约为十公里量级，10 km缓冲区分析会受到格点中心归属和边界误差影响。细粒度样例优先用于核心实验；不能把0.1°显示结果改标为0.01°精度。不同网格无须强制逐像元重合，可基于几何缓冲和面积权重匹配；格点中心法适合作为第一版透明基线，但要报告误差并做敏感性检查。

### 4.4 时间关系：锋面出现后几天有变化

定义事件日t0、固定的事件几何和前后窗口，先检验后1、2、3天的活动变化。事件日前后的核心比较应使用相同空间支持，避免因锋面移动而同时换海域、换面积。沿移动锋面跟随的响应可作为另一项明确分开的分析。

建议以有效观测日归一化：

`前期日均 = 前期小时总量 / 前期有效日数`

`后期日均 = 后期小时总量 / 后期有效日数`

`相对变化 = (后期日均 - 前期日均) / 前期日均`

如有效面积随日变化，进一步使用小时/(有效平方公里×日)，并声明面积与覆盖口径。前期为零时不强行生成有限增幅，应报告新增活动、绝对差及零基线状态。

### 4.5 非锋面对照与历史可比事件

先遵循现有“同日、同海区、距全部锋面至少50 km、面积可比”的对照约定；再评估离岸距离、水深、季节与渔具等背景是否相近。距离50 km是一项抽样限制，不自动保证两组可比。

可以同时比较锋面组与对照组的前后变化，减少整个海区活动同步升降的干扰。若要给差分结果因果解释，还需验证额外识别假设，不能仅凭有对照就宣称锋面导致鱼群或作业增加。

历史相似事件先按同海区、相近季节窗口检索，再按几何、持续性与温差等指标分层。它与“往年同一天有锋面比例”是两个不同功能。[相似事件定义](../../CONTEXT.md)、[路线图](../ocean-fishery-operation-roadmap.md)。

## 5. 用线上数据演示一个能够落地的分析起点

条件：2024-08-05；出发点124.5°E/30.2°N；锋面取120-128°E/27-34°N固定窗口、0.05°；活动取同日0.1°全量返回格点。

| 检查 | 这次计算结果 | 解释 |
|---|---|---|
| 最近编号锋面 | 此窗口中的F003，约15.67 km | 只计算编号简化折线；未把未编号短线纳入最近距离 |
| 20 km作业圈 | 格点中心落入圈内的返回活动格点1个，活动小时和0.50 | 格点中心法，未按边界相交面积折算，不能当作精确圈内总活动 |
| 30 km作业圈 | 返回格点3个，小时和14.00 | 仍未对AIS覆盖做修正 |
| 30 km内最高活动格点 | 124.7°E/30.0°N，10.19小时 | 是单日该圈内最高返回格点，不是已识别的长期生物渔场 |
| 该格点到最近编号锋面 | 约6.13 km，到出发点约29.39 km | 可以说明空间靠近，不能单日证明增强或预测价值 |
| 10 km圈 | 无返回格点中心 | 不能把它转述为“附近无捕捞活动”或“没有鱼” |

距离采用以出发点纬度换算的局部公里平面、点到折线段最短距离；由线上返回值在本次核对中计算，不是既有产品承诺。该分析未使用航线、渔获、AIS有效覆盖或跨日追踪。

另一个值得修复的问题：线上现有响应表的8月5日事件是F002；在这次固定窗口返回的编号几何中，F002距出发点约90.37 km，并非最近的F003。编号可能随裁剪窗口和对象生成过程变化，不能只凭ID字符串就跨数据版本匹配；这进一步要求保存稳定事件身份、几何来源和空间校验。

所以，“同日表里有增强”不能直接当成“出发点附近最近锋面有增强”。当前主页面响应查表只接收日期和半径，未接收用户位置或选中锋面。[查表入口](../../frontend/prototype/prototype-data.js#L893)。

## 6. 统计工作已经做到哪一步

### 已有的三层能力

1. **页面统计**：固定锚点同期抽样；近期、月、年视图；当前规则评分。同期表含2015-2024每年8月5-7日共30个日期。
2. **历史服务**：按经纬度和`radius_deg`读取历史资料，提供同月同日、月度、时间序列等汇总以及样本可靠性、缓存信息。注意这里的度数窗口不自动等于前端以公里表示的圆形作业圈。

因此，项目不是“尚无统计”，而是已有描述统计和第一版研究实验，但完整验证尚未完成。

### 统计方面仍欠缺的关键工作

| 缺口 | 当前问题 | 达到有效结果的验收 |
|---|---|---|
| 地点和事件绑定 | 离线同期固定锚点；响应只按日期/半径查表；不同窗口ID可能变化 | 换地点、换选中对象后结果正确变化；事件记录可追到几何、来源版本与窗口 |
| 等长或日均比较 | 当前转换直接用post1-3与pre7字段比较，没有按7/3天归一化 | 字段声明总量/均值/有效日；按一致单位重算，并保留旧口径用于对照 |
| 缺测分母 | 固定同期表只要求至少1个有效像元；历史服务按已生成timeline计样本 | 统一有效水域与覆盖门槛；全缺测不能成为“无锋面”有效负例 |
| 源粒度和边缘窗口 | 事件日期不等于完整前后资料；7月初需6月，8月底需9月 | 每条事件记录有效日、数据分辨率、完整窗口与缺失原因 |
| 空间/时间非独立 | 连续事件的前后窗口重叠，三档buffer嵌套 | 按事件/时间块/海区分组重采样；不将186行当独立重复 |
| 事件选择与对照 | 当前每天只一条事件，未呈现全事件选择依据 | 保存入选与未入选事件、匹配规则、对照分布与敏感性检查 |
| 总量去重 | 三个嵌套buffer的小时不能相加为海区总量 | 单独选择一个buffer或使用互斥距离环、空间并集去重 |
| 效应量和稳健性 | 有p值不等于实际差异重要，也不等于因果 | 报告绝对差、相对差、中位数、区间与跨年份/季节一致性 |
| 留出验证 | 当前示例展示与正式独立评估还未形成完整协议 | 提前确定目标与规则，在未参与调参的时段/海区复核 |

历史服务还存在性能与语义同时改善的机会：`history.py`先遍历全部历史文件形成timeline，再筛选同日与月份；冷查询成本较高，且当前实现的计样本分母需要复核。可先保存按地区/格点的每日基础量，再按所需月份与有效日期聚合，而不是每次扫描数十年文件。[历史构建](../../backend/app/history.py#L573)、[同期分母](../../backend/app/history.py#L637)。

## 7. 预测方面的真实进度与可行方向

### 当前做到的部分

页面`baselineSeries`由当前锋面规则分、最近最多4个可用观测日期的趋势与持续性、固定同期频率以及未来天数衰减构成1/3/7天参考。主页面的把握度仍未加入AIS响应、海温或海况，也不是校准后的概率。[评分](../../frontend/prototype/prototype-fishing.js#L225)、[规则参考](../../frontend/prototype/prototype-fishing.js#L1337)。

本次检查到的是规则参考、历史追踪和分析解释；没有找到与该产品目标相配套的训练模型、严格时间切分、基线对照和独立预测评估产物。LLM任务解析也不承担海洋或捕捞活动预测。

### 先选择一个可验证目标

| 目标 | 可行性与意义 | 最少需要什么 |
|---|---|---|
| 未来1-3天局部锋面是否持续存在 | 可以作为环境预测第一步 | 连续锋面观测、明确的区域和事件定义 |
| 未来1-3天活动密度或热点是否持续 | 与已有AIS资料和产品需求更接近 | 完整联合日期、有效覆盖、热点标签与历史活动特征 |
| 未来高渔获/收益 | 当前缺可靠真值 | 渔获、鱼种、作业投入、船舶与渔具等额外资料，不适合近期承诺 |

建议先从**活动热点持续性**或**锋面持续性**二选一，避免同时把预测对象混成一个含义模糊的百分比。

### 预测的最小验证方案

1. 在2017-2024联合覆盖且质量足够的日期与海域建立样本，固定数据版本和覆盖要求。
2. 特征只能使用预测时刻及之前的信息：过去活动密度、过去出现天数、最近锋面距离、锋面持续性、当时温差代理、季节等。
3. 标签来自未来1/3天真实观测；历史响应表的post1-3本身是未来结果，不能在事件日作为已经知道的预测输入。
4. 先比较“延续昨天”“近7天平均”“同季节基线”。再评估简单可解释模型是否确实增加价值。
5. 按时间先后留出验证和测试，例如在覆盖足够时训练2017-2022、验证2023、最终测试2024；这只是建议的协议，不是当前已完成实验。重叠标签窗口之间设置适当隔离，必要时再做留出海区。
6. 若输出小时/密度，报告MAE等误差；若输出热点概率，报告精确率、召回率与概率校准；若输出候选区域列表，比较前K个区域命中未来热点的比例与基线，并同时报告覆盖和候选数量。
7. 没有超过基线，仍保留描述统计和规则参考，不包装成成熟预测。

时间顺序验证的基础原则可参考[scikit-learn TimeSeriesSplit官方说明](https://scikit-learn.org/stable/modules/generated/sklearn.model_selection.TimeSeriesSplit.html)；本项目还需要针对空间相关与重叠事件自行设计分组。这个建议不是已经实现的模型方案。

若以后面向真实出海日，还需接入足够新鲜的近实时观测或业务预报、明确发布延迟并持续监测。现有至2024年的资料适合历史回测，不直接支持2026年实时业务预测。

## 8. 可视化加速：先保证分析正确，再让用户快速比较

已有实现包含RLE、图形合并、多级底图与LOD、420 ms视野防抖、窗口余量与对齐、请求合并、概览预取以及服务端缓存。项目已有加速工作，缺的是统一链路下的测量、正确性与优化收益证据。

建议把耗时拆成：服务器读取/计算、序列化、传输、解析、数据适配、地图绘制、面板统计。地图拖动、换日期、改变范围、展开统计应分别记录，而不是只报告一个最快接口响应。

| 优先级 | 工作 | 验收 |
|---|---|---|
| P0 | 对齐线上/本地版本与数据路径 | 当前页面所需接口存在；source/coverage正确；保留离线回退 |
| P0 | 校验请求日期与缓存身份 | 快速切日/平移不会显示旧日结果；缓存包含日期、范围、步长与来源版本 |
| P0 | 建立代表性操作的性能基线 | 冷/热p50、p95、传输量、绘制时间、峰值内存与数值正确性一起记录 |
| P1 | 减少整图与隐藏页签重复工作 | 保留底图；仅重绘变化图层；隐藏页签延迟计算；相同操作数值不变 |
| P1 | 历史基础量预计算与查询索引 | 查询不再每次扫全部历史文件；有效分母一致；更新后可失效重建 |
| P1 | 活动图显示聚合与完整统计分离 | 聚合保留总小时；筛掉的显示点不丢失于分析；揭示显示层级 |
| P1 | 几何索引和有限日期预取 | 最近距离仍基于原几何；播放不会无限累积内存 |
| P2 | 根据主耗时选择更复杂技术 | 绘制瓶颈再试Canvas/WebGL；多维聚合瓶颈再试分析数据库/预聚合索引 |

候选瓶颈的源码证据包括`drawMap`整图清空与`refresh`全页签更新，以及历史冷查询全文件遍历；它们仍需测量确认，不能据此声称已经知道实际耗时排名。WebGL也有显存预算、批量绘制和资源管理成本，不是自动加速保证。[MDN官方指南](https://developer.mozilla.org/en-US/docs/Web/API/WebGL_API/WebGL_best_practices)。

更完整的源码核对见[可视化加速专项笔记](ocean-visualization-acceleration-audit-2026-10-21.md)。其中关于新视野接口和日期一致性的内容是本地代码风险检查，不是已复现的线上故障。

## 9. 建议按三个里程碑推进

### M0：让同一次分析可信且可追溯

交付：版本与接口清单；逐日逐层覆盖表；稳定事件身份；响应绑定当前事件；统一km圆形/度数窗口语义；前后日均或等长窗口；正确的缺测分母；性能基线。

验收：同一任务条件在地图、统计、响应卡和导出报告中一致；换位置不会沿用异地响应；缺测不会变成0；有前后窗口/来源可追溯记录。

### M1：完成一个真实“锋面-活动关系”分析流程

范围：先用已有2024年7-8月东海样本，并补齐该窗口所需的6月底/9月初前后资料；再扩展多年相同季节。

交付：附近活动热点、最近锋面、关系连线、互斥距离带活动密度、前后曲线、非锋面对照、多半径敏感性与复核报告；基础加速并行推进。

验收：选一个事件能从地图走到同一事件的统计表；正例和无明显变化例都可复核；报告样本数、区间、覆盖和不确定性，不只给推荐分。

### M2：验证泛化与预测增益

范围：利用2017-2024质量足够的共同资料，做多年份、多季节和留出时段评估。

交付：相似事件检索；更符合事件相关性的统计检验；一个明确预测对象的基线与模型对比；性能对照实验。

验收：规律在未参与规则选择的样本上仍成立，或如实说明不稳定；预测须超过约定基线；优化结果在数值一致前提下改善延迟/内存，而非仅丢弃数据。

## 10. 最先值得开的工作包

建议名称：**附近锋面与捕捞活动关系分析闭环**。

最小交付内容：

1. 核对部署版本、接口路径与各层数据清单。
2. 将用户位置、作业圈、日期、选中锋面事件与数据版本作为统一分析条件。
3. 输出最近锋面、活动热点和两者距离关系，保留完整分析数据。
4. 对单一事件生成10/20/30 km窗口、前期日均、后期日均与非锋面对照。
5. 同步记录缺测、有效天数、有效面积、来源与参数。
6. 生成地图、曲线、统计表相互对应的一份报告。
7. 以直接计算作为正确性参照，记录读取、传输、绘制与统计耗时。
8. 用一个正例、一个无明显响应例及一个缺测例验收。

该工作包能够同时澄清“分析什么”“怎样得到有效结果”和“加速谁”，比单独更换地图技术或增加一个预测分数更容易形成可验证成果。本文只提出方向，没有改动应用实现或上线状态。
