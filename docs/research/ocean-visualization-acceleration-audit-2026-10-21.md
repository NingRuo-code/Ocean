# Ocean 可视化与查询加速专项核对

核对日期：2026-10-21。范围：本地实现、项目说明、已有论文选型笔记。此核对没有调用线上站点、运行性能压测或修改应用；下述瓶颈属于代码支持的候选归因，不是已经测出的耗时排名。

## 结论

下一步适合先做“测量并减少无效工作”，再根据主要耗时决定是否引入新的查询索引或渲染技术。当前已有不少按需出数、压缩、LOD 和缓存，不能把项目描述为尚未开始加速；也没有证据把它称为完整 imMens/GPU 数据立方体复现。

加速必须服从分析语义：显示层可以粗化，分析层必须保留总小时数、有效观测分母、对象几何与缺失状态。尤其不能使用地图实际画出的 700 个活动点计算区域全部活动量。

## 2. 先厘清数据路径，防止优化错接口

当前 `prototype-data.js:331-334` 的 `viewportUrl` 走 `/api/viewport`。本地 `backend/app/main.py:141-153` 调用 `build_cached_viewport`，后者在 `backend/app/viewport.py:192-207` 构建 `build_static_prototype_viewport`。此路径在 `539-625` 读取静态原型导出数据，并声明 `static_prototype` 和覆盖范围。

另有 `/api/frontend/day/{date}`（`backend/app/main.py:402` 起）和 `frontend_payload.py` 的 raw NetCDF 出数。两条路径不等同。旧 README 和源码注释的某些性能说法主要针对后一条；不能把“raw 产品是全球”直接推导成当前 `/viewport` 对所有日期、全球窗口都有效。线上部署可能与本地版本不同，应由主核对任务检查 API 返回的 source/coverage，而不是猜测。

## 3. 优先排查的成本与正确性问题

### 3.1 浏览器重复绘制与重复计算

- `prototype-fishing.js:827-875` 的 `drawMap` 会先 `svg.innerHTML = ""`，再重建地图、底图、数据、标签与选择层。图层切换、数据预取完成等操作可能触发整图重画。候选优化：稳定底图层、栅格层、对象层、标记层分开更新，缓存与数据版本/投影相关的 path。
- `prototype-fishing.js:1872-1893` 的 `refresh` 同时执行当前、未来、历史、依据与 AI 的渲染，即使某个页签不可见。候选优化：按状态依赖失效，只重算受影响的结果；隐藏页签延后渲染。
- `prototype-fishing.js:175-188` 为每个对象求最近位置并排序；指针查询也计算最近锋面（`920-950`）。对象增多时，可建立对象包围盒或线段空间索引；这不会改变距离定义。
- `prototype-data.js:632-678` 的跨锋面海温差需沿线两侧取样。可按日期/对象/偏移距离/数据版本缓存这一代理指标，但不能把代理温差标成原始 frontal_intensity。

### 3.2 请求生命周期与日期一致性

- `fetchPatch` 的在途、失败记录使用传入 key（`prototype-data.js:499-522`），窗口 key 由 bbox+step 构成（`265-266`），没有包括日期；多日期并行预取时应专门验证是否串用请求或抑制请求。
- `requestViewportPatch` 以窗口是否变化决定是否请求（`prototype-fishing.js:2124-2127`）。它没有把日期变化纳入该判断；换日期仍处同窗口时要验证是否确实拿到该日的视野片。
- 该视野请求完成回调（`2134-2142`）未像 `loadThenRefresh` 一样先检查 `state.date === iso`。建议引入完整请求身份、最新请求序号、必要的取消机制；旧结果可以留在自身缓存中，但不应覆盖新任务显示状态。
- 这是代码层面需要测试的风险，不是本次已复现的线上事故。

### 3.3 内存与缓存失效

- 每天最多四片不限制已访问日期总数；`PATCHES`、DAYS/SST、FISHING.days 持续播放多年日期时可能增长。建议记录内存，再做跨日期上限、按需预取和最近访问淘汰。
- `/viewport` 缓存键包含日期、bbox、step 和契约版本（`viewport.py:132-147`），未直接携带源文件内容指纹。数据更新时应保证版本/失效策略同步，否则命中缓存并不证明结果是最新源数据。
- 热点缓存预热应先覆盖常用海域与日期；“全历史全窗口预计算”会迅速放大磁盘与更新成本。

### 3.4 活动图绘制筛选不是科学聚合

`prototype-fishing.js:720-745` 按当日小时数第 60 分位筛选，再取最高 700 个格点绘圆点。注释说“低于中位数不画”，实际阈值为第 60 分位。它能减少视觉拥挤，但省略了活动格点，不能用“图上没点”判断无活动。

更合适的下一步是：屏幕网格聚合保持 fishing_hours 总和，点击可看原始格点详情；区域统计单独按完整分析数据计算。提示用户概览分辨率、显示点数和原始记录数。抽样、显示聚合、分析统计应明确分离。

## 4. 建议执行顺序与验收

| 优先级 | 工作 | 验收方式 |
|---|---|---|
| P0 | 核对线上/本地接口链、请求日期身份、覆盖语义、缓存失效 | 同窗口换日期、快速连续切换、失败重试、新旧数据版本各有一致性案例 |
| P0 | 给当前路径建立分阶段耗时记录 | 分清服务器计算、序列化、传输、JSON解析、数据适配、绘制、面板计算，不只测整个请求 |
| P1 | 只刷新受影响页签与图层，复用底图/path/对象指标 | 同样输入和操作，数值与对象ID一致；比较浏览器长任务和帧耗时 |
| P1 | 日期预取与内存上限，热点缓存，几何索引 | 报告命中率、峰值内存、请求数、冷热 p50/p95 与数据规模 |
| P1 | AIS完整统计与显示聚合分离 | 每个聚合窗口总小时与直接求和一致；无覆盖不变成零 |
| P2 | 日期区间+地图+活动时间序列共享过滤与聚合查询 | 使用同一批数据和统计口径，比较朴素扫描、现有缓存、分析数据库/预聚合方案 |
| P3 | 只有绘制仍为主瓶颈时试 Canvas/WebGL；只有聚合仍为主瓶颈时试多维索引 | 把实现成本、首次加载、构建时间、内存和正确性一起报告，不只报告最快一帧 |

建议性能目标可以预先制定，例如拖动反馈、切日可用时间、统计查询 p95，但具体阈值应在指定设备、网络和数据规模下由团队确认；这里不把任何阈值写成已经实现的指标。

最小实验矩阵：小/中/全球三种视野；少/多锋面与活动格点日期；首次/重复查询；原始明细/概览；仅环境/叠加活动；单次切日/连续播放。避免在生产服务器直接做并发压测，先使用离线或独立测试实例。

## 5. 与论文路线的关系

已有笔记 `docs/research/ocean-aggregation-paper-alternatives-2026-10-16.md` 区分了 imMens、Mosaic 等的应用条件。当前代码检索未发现 WebGL/GPU roll-up、DuckDB 或 Mosaic 的接入实现。

- 若主要成本是 SVG 重建、几何投影、传输，先改现有渲染和LOD，换查询框架不自动解决这些成本。
- 若新增地图、日期区间、活动时间序列与统计卡的共享过滤后，查询聚合成为主要成本，再以小切片对照验证数据库内预聚合/协调查询路线。
- imMens 可以作为分桶与多尺度瓦片的方法参考；普通视口裁剪和缓存不足以称为完整复现。
- 前端加速、查询加速不会自动证明锋面与捕捞活动的科学关系。后者仍需空间匹配、有效日期归一化、对照与独立验证。
